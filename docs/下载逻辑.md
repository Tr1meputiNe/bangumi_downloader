# 下载逻辑（现状说明，供检查）

这份文档把「从判断该不该下，到文件落盘」的**全部规则**按顺序写清楚，
方便一条条核对。括号里是这台机器上 config.json 的**实际取值**
（`—` 表示配置里没写、用的是程序默认值）。

---

## 一、三层时钟：什么时候才会真的动

### 第 1 层：Windows 计划任务（外部时钟）

任务 `BangumiDownloader` 的触发器是**按播出时间排**的（不是每 15 分钟无脑跑）：

```
每集一段窗口：从「播出 + readyDelayMinutes(60)」开始，每 activeIntervalMinutes(15) 分钟触发一次，
             持续 releaseWindowHours(12) 小时
一条重读计划：每 idleIntervalMinutes(180) 分钟一次，一直重复
登录时触发：  重启后补上错过的
```

实例策略 `MultipleInstances=IgnoreNew`：上一轮还在跑时，这次的触发被拒
（退出码 0x800710E0，界面上显示「上一轮还在跑，这次触发跳过（正常）」）。

### 第 2 层：程序内的计划判定（`data/auto-schedule.json`）

同一份计划文件里记着 `nextCheckAt`（下次**真干活**）和 `nextRefreshAt`（下次**只重读计划**）。
每一轮触发进来先看：

| 情况 | 动作 | 网络请求 |
| --- | --- | --- |
| 现在 ≥ nextCheckAt | **run**：真去搜种、下载 | 有 |
| 现在 ≥ nextRefreshAt 但没到 nextCheckAt | **refresh**：只问一次 Planner 重算计划 | 1 次 Planner |
| 都没到 | **skip**：直接退出 | **0 次** |

> 计划文件缺失/损坏/时间不合法时一律按 run 处理（宁可多跑一轮，也不能因为坏文件停摆）。
> 跳过时的日志只在「原因变了」的时候打一遍，避免刷屏。

### 第 3 层：手动触发

网页「立即跑一轮 / 试跑」和命令行 `--force` 会**忽略计划**立刻执行（`--dry-run` 同理）。

## 二、要下什么（每部番的「下一集」）

1. **Planner 优先**（`plannerBaseUrl`，默认取「在看」`collectionTypes=[3]`）：
   拿每部番「已播出 + 未看」的集号。
   连不上 Planner → **退回本地 `watchlist.json`**（那里按 `lastEpisode`/`completedEpisodes` 推算下一集）。
2. **播出时刻缓冲**：`airdate + airTime + readyDelayMinutes(60)` 之前不搜
   （片源站通常播出后 30~60 分钟才出种）。
3. **已经下过的集不再下**：`auto-schedule.json` 的 `done` 列表记着「哪一集下完了」。
   Planner 的「未看」只反映**你看没看**，不反映我们下没下过 —— 没有这层的话，
   一集下完之后每 15 分钟都会再搜一遍同一个种子，直到你把它看完。
   *只有整包下完才记 done；下到一半的不记，下一轮继续。*
4. **集号匹配**：
   - **严格**：候选集号 == 目标集号（Planner 用季内编号，例如「第 13 集」）
   - **放宽**（严格匹配可用候选 < 3 条时才启用）：同一部番、**单集**发布、
     集号 > 目标集号（编号偏移只会让数字变大）、发布时刻在目标集播出之后、
     集号不超过目标 + 200。按打分排，**排在严格匹配之后**。
     *例子：Planner 说第 13 集，字幕组按全季连续编号写成 S01E25 —— 就是靠这条认出来的。*
     日志会明确写：`严格匹配只有 1 条可用，另有 4 条疑似同一集（集号 25/25/25/25…）`

## 三、一个目标集内部：挑哪条候选下

```
候选排序（打分：容器/分辨率/字幕/字幕组/做种数/是否合集）
   ↓
① 续传探测：磁盘上已经有这个种子数据的候选，直接续传（按「真实数据量」判断，预分配不算）
   ↓ 观察窗口 15 分钟
   ├─ 拿到了 ≥8MB → 继续用它下到底（不打断健康下载）
   └─ 拿不到    → 记成兜底结果，去试别的候选
   ↓
② 逐条试跑：每条候选试 trialSeconds(75) 秒
   ├─ 完整下完            → 成功返回
   ├─ 收到 ≥ minThroughputKBps(20) → 用剩余预算继续下到底
   ├─ 收到数据但不达标     → 记成兜底，继续试下一条
   └─ 完全没收到数据       → 清掉试跑产生的空目录，换下一条
   ↓
③ 全都不达标但有兜底 → 用「收到最多」的那条继续下（慢但能下 ≠ 下不动）
   ↓
④ 一条都没收到数据 → 本轮失败，退避后重试
```

每一轮开始前会**重新搜一遍**候选（新番刚播完时只有一两条 raw，字幕组版本要晚几个小时才出），
新候选排在前面，旧的留着兜底。

**什么时候算「这条不行」**：

| 条件 | 取值 | 说明 |
| --- | --- | --- |
| 单条候选总超时 | `timeoutMs` = 60 分钟 | 单次尝试的上限 |
| 卡死判定 | `stallTimeoutMs` = 3 分钟 | 3 分钟没有任何分片完成就放弃这条 |
| 续传看门狗 | 150 秒 | 续传时 150 秒没有新增就判定这条已死 |
| 试跑窗口 | `trialSeconds` = 75 秒 | 判断「有没有速度」的观察窗口 |
| 最低速度 | `minThroughputKBps` = 20 | **判断口径是「收到的字节 / 时间」**，不是「已校验的分片」 |
| 一轮最多试几条 | `maxAttempts` = 12 | 试跑最坏 12×75 秒 ≈ 15 分钟 |
| 单轮时间预算 | `budgetMinutes` = 240 | 一轮（一次命令）的总时间上限 |
| 重试轮数 | `retryRounds` = 8 | 一轮没下完就再来一轮 |
| 退避 | 5 分钟起，×2，上限 60 分钟 | 轮与轮之间等多久 |

**放弃的条件**（会一直重试到这些为止）：所有候选都收不到任何数据 → 本轮失败 →
退避后下一轮；或者这一集的窗口（`releaseWindowHours` = 12 小时）过了 → 不再密集检查，
退回每 180 分钟一次的节奏。

## 四、文件落在哪、叫什么

```
savePath(D:/anime_download)
├── 番剧/                                  ← seriesDir：所有番剧内容都归纳在这里
│   └── <发布名或种子名>/                    ← 一部番一个文件夹
│       ├── xxx.mkv
│       └── ⚠ 还没下完，现在播放会失败.txt     ← 没下完时才有，带实时分片进度；下完自动删
├── .bangumi-meta/                         ← 种子元数据缓存、本地内容清单
└── bangumi-downloader/                    ← 程序本体
```

- 多文件种子：文件夹用种子自带的名字
- 单文件种子：文件夹用**发布标题**（否则单集会散落在根目录）；
  但**磁盘上已经有这个种子时，优先复用它原来的目录名**（避免同一个种子出现两份）
- 断点续传会把文件预分配到完整长度 —— 所以**看文件大小判断不出进度**，
  要看：目录里的标记文件、网页界面、或者「片库」页的「核对」（分片哈希校验）

## 五、互斥与去重（同一个东西不许被下两遍）

| 机制 | 作用范围 | 说明 |
| --- | --- | --- |
| `data/.bangumi.lock` 单实例锁 | auto 各轮之间 | 计划任务和手动 auto 不会同时跑 |
| `data/downloading.json` 登记簿 | **跨进程** | 网页的任务队列和计划任务的 auto 共用一个登记簿，按 infohash 认领；被别的活进程占着就跳过（拒绝时会说明是谁在占） |
| `done` 列表 | 跨轮 | 已下完的集不再重复下载 |
| `MultipleInstances=IgnoreNew` | 计划任务内部 | 上一轮没跑完时，新的触发直接跳过 |

## 六、这台机器的实际参数一览

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `readyDelayMinutes` | 60 | 播出后 60 分钟才开始找种 |
| `activeIntervalMinutes` | 15（默认） | 正在等片源时多久检查一次 |
| `idleIntervalMinutes` | 180（默认） | 重读计划的间隔 |
| `releaseWindowHours` | 12（默认） | 一集最多密集盯 12 小时 |
| `trialSeconds` | 75 | 每条候选试跑多久 |
| `minThroughputKBps` | 20 | 最低速度（按收到的字节算） |
| `maxAttempts` | 12 | 一轮最多试几条候选 |
| `probeCandidates` | 10 | 探活几条候选 |
| `budgetMinutes` | 240 | 一轮总预算 |
| `timeoutMs` | 3600000 | 单条候选超时 60 分钟 |
| `stallTimeoutMs` | 180000 | 卡死判定 3 分钟 |
| `retryRounds` | 8 | 重试轮数 |
| `retryBackoffMinutes` / `retryMaxBackoffMinutes` | 5 / 60 | 轮间退避 |
| `maxEpisodesPerSubjectPerRun` | 999 | 单部番单轮不限集数 |
| `seriesDir` | 番剧 | 归纳目录 |
| `collectionTypes` | [3] | 只追「在看」 |

## 七、今天改动过的地方（含我自己引入的错误）

| # | 现象 | 原因 | 修法 |
| --- | --- | --- | --- |
| 1 | 核对报告把下好的番说成「空壳」 | 内容归纳进 `番剧/` 之后，verify 还按旧布局找文件 | 按实际布局定位（番剧子目录 / 旧根目录 / 单文件发布名三种都认） |
| 2 | 正常的 MP4 被报「播不了」 | moov 是最后一个 box 但有 1.44MB，只扫尾部 1MB 扫不到盒头 | 改成沿顶层 box 逐个跳 |
| 3 | 一直在收数据，已完成分片却几乎不涨 | **分片的 block 缓冲挂在 peer 上，待发队列是全局的** —— 一个分片的 block 来自多个 peer 时，拼装只用最后一个 peer 那份，另一半是空的，SHA1 必失败 | 缓冲改成按分片存 |
| 4 | 「文件 912MB 却播不了」 | 断点续传会把文件预分配到完整长度，大小是假的 | 目录里放标记文件（带进度），下完自动删；界面显示真实进度 |
| 5 | 「已有 913MB 进度」其实是空的 | 续传判定用了文件**名义长度** | 改成抽样估算**真实数据量** |
| 6 | 同一个种子出现两份目录 | 单文件种子的目录名从「种子内文件名」改成「发布标题」，老目录没被复用 | 先按 locateTorrent 找已有目录，找到就写进去 |
| 7 | 速度一直显示 0.00 MB/s | 速度按「完成的分片」算，2MB 一块，慢链路 75 秒凑不齐一块 | 改按「收到的字节」算 |
| 8 | **「15 分钟之内没下完就被中断」** | 我加的「续传只给 15 分钟」到点就掐，86% 的健康下载被硬切断 | 15 分钟改成**观察窗口**：在动就继续下到底，不动才换候选 |
| 9 | 慢链路永远被判「下不动」 | 试跑吞吐也按「已校验分片」算，低于约 27 KB/s 恒为 0 → 每 75 秒扔掉候选重来 | 改按收到的字节；且全部不达标时保留「收到最多」的那条继续下 |
| 10 | 两个一起在下 | 网页任务队列和计划任务 auto 是**两个进程**，锁互相看不见 | `data/downloading.json` 跨进程登记簿，按 infohash 认领 |
| 11 | 计划任务报「异常退出」 | 0x800710E0（上一轮还在跑，触发被跳过）被当成异常 | 单独翻译成「上一轮还在跑，这次触发跳过（正常）」 |

## 八、已确认的默认行为（2026-10-04 确认）

下面五条是当时列出来、用户逐条确认过的。改成别的行为之前要先说清楚为什么。

1. **最低速度 `minThroughputKBps`(20) 是「偏好」，不是硬门槛。**
   它的作用是**比较候选**：谁快用谁。所有候选都达不到 20 KB/s 时，仍然挑「收到最多」
   的那条继续下 —— 因为这台机器的链路对公共种子经常只有 10~40 KB/s，
   设成硬门槛等于永远不下。慢但能下 ≠ 下不动。

2. **磁盘上有旧进度、同时新出了更好的版本：先续传。**
   续传的观察窗口是 15 分钟：在动（≥8MB）就继续下到底，**不打断**；
   不动才换别的候选。理由：已经下到 86% 的东西重下是纯浪费，
   而「新版本更好」只体现在速度上，续传那条只要在动就不亏。

3. **一集同时只允许一个下载（跨进程登记簿）。**
   网页手动下载撞上计划任务正在下的同一个种子时，**直接拒绝并说明谁在占**
   （`data/downloading.json` 里记着 pid、开始时间），不做排队。
   理由：拒绝的理由一眼能看懂；排队会让人以为「点了没反应」。

4. **放宽集号匹配默认开启。**
   Planner 按季内编号（第 13 集），多数字幕组按全季连续编号（S01E25）——
   严格匹配往往只剩一条没种的 raw。放宽规则：同一部番、单集发布、
   集号更大、发布于该集播出之后；**排在严格匹配之后**，日志会写明认了哪几条。
   这是能下到当集的关键；残余风险（认错集）由「播出时间之后」这一条挡住大半。

5. **每集最多密集盯 `releaseWindowHours`(12) 小时**，超过就降频到 180 分钟一次。
   冷门番可能一直没有种，12 小时后不再每 15 分钟去搜（仍然会按兜底节奏重试，
   而且片源出现时下一轮就会下）。

## 九、还有一条隐含约定

**「正在下载」这条状态必须与进程同生共死。** 计划文件里的 `running` 字段记 pid，
读的时候进程不在了就当没有（并清掉残留）—— 否则进程被杀之后界面会一直显示
「正在下载 0%」，看着像卡死（实测出现过）。
